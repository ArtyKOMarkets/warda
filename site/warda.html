Economic authority for autonomous agents

A spending limit the network enforces.

Give an agent its own key and a budget on Kaspa L1. It spends directly — no co-signing, no relay, no custody — and consensus rejects anything outside its limits. You sign once, then go offline.

If the agent key is stolen outright, the thief inherits exactly the same limits. That is the whole idea.

The distinction the whole protocol rests on

Where does the limit actually live?

In your process

The usual pattern: fund a hot wallet with "only what the agent should spend," and keep a running total in the code that pays.

A real agent-payments library in production today caps spending with an environment variable, and its own documentation says the server "refuses further calls until restarted."

So the cap resets when the process does. It is bypassed by a crash, a redeploy, a second instance, or anyone who reads the key out of env. The wallet balance is the only true limit.

In consensus

A Warda grant is a UTXO locked by a covenant. The budget, the per-spend cap, the epoch allowance, the expiry and the payee allowlist are part of the script that unlocks the coin.

A spend that exceeds any of them is not refused by a server. It is an invalid transaction — no node will relay it and no miner can include it.

Restarting changes nothing. Nor does compromising the agent. The limits are not enforced by the code holding the key.

What a grant is

Six constraints, and three keys that mean different things.

A grant is state encoded into an address. Change any field and you have a different address — which is why a grant cannot be edited, only spent forward.

FieldWhat it binds
budgetTotalThe most this grant can ever spend, across its whole life and every child it delegates to.
maxPerSpendA ceiling on any single payment. Caps the blast radius of one bad decision.
epochLimitA rate: how much may be spent per epochLength blocks. Bounds how fast a compromise drains.
notBefore / expiresAtA validity window. After expiry the principal may sweep the remainder back.
recipientsRootA Merkle root over the allowed payees. Every spend carries an inclusion proof; there is no way to pay anyone else.
delegationDepthHow many further levels of sub-agent this grant may create. Zero means it is a leaf.
KeyPowerHeld by
agentKeySpend, within the limits. Delegate to sub-agents.The agent, online, on the machine doing the work.
revocationKeyStop the grant. Sweeps the balance to the principal — it can never redirect it elsewhere.A monitor or kill-switch that you do not have to trust with the money.
principalKeyReceive. Reclaim the remainder once the grant expires.The owner. Signs once at creation, then offline.

The split between revocationKey and principalKey is load-bearing, and it took a real bug to make it true. An earlier version let the revocation path burn the balance to fees, and a later one let it sweep a delegated child anywhere it liked — both making a "stop" capability into a "destroy" or "take" one. Both are fixed, and both now have an attack test that fails if they come back.

Install

Two packages. Nothing to compile.

Compiled JavaScript with TypeScript declarations. Node 20 or newer, no build step, no Rust toolchain, no Silverscript compiler — address derivation splices values into a compiled covenant template that ships with the package.

# the SDK: build, sign and verify grants
npm install @warda/kaspa

# the MCP server: hand an agent framework a Warda tool
npx @warda/mcp

Creating a grant

import { buildGenesis, attachGenesisSignature, signDigest, RecipientSet } from "@warda/kaspa";
import template from "@warda/kaspa/covenant-template.json" with { type: "json" };

// Who this agent is allowed to pay. Committed as a Merkle root.
const payees = new RecipientSet([vendorA, vendorB]);

const grant = {
  authority: { principalKey, revocationKey },
  state: {
    agentKey,
    budgetTotal:  1_000_00000000n,  // 1000 KAS, ever
    maxPerSpend:    200_00000000n,  // 200 KAS, per payment
    epochLimit:     500_00000000n,  // 500 KAS ...
    epochLength:            1000n,  // ... per 1000 blocks
    recipientsRoot: payees.rootHex,
    notBefore, expiresAt,
    delegationDepth: 2n,
    /* accounting starts at zero */
  },
};

const unsigned = buildGenesis({ template, grant, funding, changeScriptPublicKey, fee });
const tx = attachGenesisSignature(unsigned, signDigest(unsigned.sighash, principalSecret));

The agent spends, on its own

import { signSpend } from "@warda/kaspa";

const { tx } = signSpend({
  template, authority, state,
  utxo,                            // the grant's current coin
  amount:   50_00000000n,
  recipient: vendorA,
  proof:     payees.proof(vendorA), // proves the payee is allowed
  claimedDaa, fee, computeBudget: 16,
}, agentSecret);                    // the principal is not involved

The SDK deliberately does not decide whether a spend is allowed — the covenant does, on chain, and it is the only thing that can. If the SDK reimplemented the rules, a divergence would fail by wrongly permitting. Reimplementing assembly fails the other way: a mistake produces a transaction the network rejects, which is loud.

Lifecycle

A grant moves through six operations.

Each one is an entrypoint in the covenant, with its own signer and its own rules. The address changes at every step, because the address is the state.

Principal signs · once

Genesis

An ordinary payment that happens to pay into a covenant address. From here the principal can go offline permanently.

Agent signs

Spend

Pay an allowlisted recipient, within every cap. The remainder continues to a new address encoding the updated accounting — budget spent, epoch consumed.

Agent signs

Delegate

Hand a sub-agent its own narrower grant, without asking the principal and without custody. The parent reserves exactly what the child receives, so authority is subdivided and never created. A child may narrow the payee list, the caps, the rate and the window — never widen any of them.

Agent + revocation key

Settle

Take a finished child back in. Its remaining coin returns to the parent, and what it spent is charged against the parent's budget. Without this, delegation would be one-way — a grant that subdivides itself would shrink permanently.

Revocation key

Revoke

Stop the grant at any time. The balance goes to the principal and nowhere else — the covenant checks the destination and the amount, so a monitor holding this key can halt an agent without being able to take or burn its money.

Principal signs

Reclaim

After expiry, sweep the remainder home. This is a right that opens at expiry, not a prohibition that closes: a UTXO covenant cannot say "must be spent before X", only "not before X".

Evidence

Fourteen attacks, run against the real script engine.

Golden vectors prove two implementations agree about a transaction meant to work. They cannot catch a covenant that permits too much. These do the other half: every attack sits beside its nearest legitimate twin, because a covenant that refuses everything would pass a suite made only of refusals.

ProbeEngineWhat it establishes
epoch-rewindrefusedThe agent picks the block height it claims. Claiming an earlier epoch once reset the allowance to zero — repeatably. The per-epoch cap limited nothing at all.

Eight of fourteen shown. Six vulnerabilities have been found in this covenant so far; none was found by reading the code, and every one is now pinned by a probe that fails if it returns.

What it is for

Anywhere software spends money without a human in the loop.

Pay-per-call APIs

Agents buying inference

An agent paying per request for compute, data or tools. Today that means a hot wallet and a counter in the client. A grant makes the ceiling a consensus rule and the vendor list a Merkle root.

Fan-out

Sub-agents with real budgets

An orchestrator splitting work across workers, each getting its own grant — narrower payees, smaller caps, a shorter window — with the parent's total never exceeded however the tree is shaped.

Operations

Bounded automation

Recurring settlement, treasury sweeps, market-making bounded by rate rather than trust. The kill switch is a key that cannot touch the balance.

Custody

Delegation without a co-signer

No multisig round-trip, no relay to bribe or DDoS, no service holding funds. The principal signs once; the agent is unattended from then on.

Integrations

A grant is a funding source with rules attached.

Which makes it a drop-in wherever an agent currently needs a private key.

Available now

Model Context Protocol

@warda/mcp exposes four tools over stdio: read a grant's authority, check whether a spend is permitted and why, check a delegation, and build an unsigned spend. It never holds a key and never enforces — it explains, and the covenant decides.

Next

x402 / HTTP 402

x402 answers how an agent pays for one call. Warda answers what it is allowed to spend, in total, and to whom. They compose cleanly: the marketplace's validated vendor list is the allowlist, and the payment step becomes a covenant spend instead of a hot-key transfer.

Built in

Kaspa nodes

The SDK speaks wRPC directly — four calls, no proxy. It refuses to route covenant transactions through third-party REST services, which silently drop the covenant binding and produce a signature that cannot verify.

Any language

The vectors ship with it

Golden genesis, spend and delegation vectors travel in the package, so a second implementation in any language can check itself against the same bytes rather than against a prose spec.

Limits

What the chain does not enforce.

Published as prominently as the guarantees, because a limit you discover in production is a bug and a limit you read first is a design constraint.

  • The epoch cap bounds one grant's rate, not a subtree's. A parent limited to 500 KAS per epoch can delegate to ten children at 500 each. The total is still bounded exactly by budgetTotal — the reserve accounting is conservative — but the rate limit degrades toward the budget limit under delegation.
  • Expiry opens a reclaim right; it does not close the spend path. A UTXO covenant can express "not before", never "must be spent before". After expiry an agent keeps spending until someone actually reclaims. A grant past its term is unattended, not dormant.
  • A grant is one UTXO, so its payments are serial. The second spend's input is the first spend's output. Delegation is the concurrency primitive: N children are N independent UTXOs and therefore N parallel lanes.
  • Narrowing a payee list follows the Merkle tree. A child's allowlist must be a subtree of its parent's — a contiguous, power-of-two-aligned run. So the order of an allowlist is a design decision: payees delegated together should sit together.
  • Settlement is last-in-first-out. The reserve is a hash chain, so the most recently delegated child must be settled first. That is the price of one hash and no proof, instead of a second Merkle fold.
  • Nothing here cancels an in-flight spend. Revocation makes the balance unreachable from the next block on; a transaction already in the mempool may still land. No UTXO covenant can say "and cancel anything outstanding".
