A spending limit the network enforces.

Give an autonomous agent its own key and a real budget on Kaspa. It spends unattended — no co-signing, no relay, no custody — and consensus rejects anything outside its limits.

The problem

Every agent that spends money today is trusted not to.

The standard pattern is a hot wallet holding "only what the agent should spend", and a counter in the code that pays. Both halves fail the same way: the limit lives in the process.

Once the server has spent that much it refuses further calls until restarted. A production agent-payments library, describing its own spending cap
A Warda grant's limits are part of the script that unlocks the coin. A spend exceeding them is not refused by a server — it is an invalid transaction. No node relays it. No miner can include it. Restarting changes nothing · neither does stealing the key

What a grant gives you

Authority you can hand over and still bound.

Budget & rate

Hard ceilings

A lifetime total, a per-payment cap, and an amount per N blocks. The first bounds exposure; the last bounds how fast a compromise can drain.

Counterparty

An allowlist, not a hope

Payees are committed as a Merkle root. Every spend carries an inclusion proof. Paying anyone else isn't rejected — no valid transaction exists.

Sub-agents

Delegation without custody

An agent can hand a worker its own narrower grant — smaller caps, fewer payees, a shorter window — without asking you, and without ever exceeding its own budget.

Exit

A stop button that can't steal

Revocation is a separate key that halts a grant and returns the balance to you — and is structurally incapable of sending it anywhere else, or burning it.

Built to be checked

The limits are published as loudly as the guarantees.

Six vulnerabilities have been found in this covenant so far. None was found by reading the code — each came from handing an attack to the real script engine and reading its verdict. All six are documented, fixed, and pinned by a test that fails if they return.
