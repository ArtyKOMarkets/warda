Warda Protocol v0.3 · Draft August 2026 Kaspa testnet-10

Give agents money.
Not unlimited authority.

Warda is an economic authority layer for autonomous agents. A principal issues a bounded grant; the agent spends against it directly; the network refuses anything outside its limits. No co-signer, no custodian, no policy server in the path.

02

The primitive is a grant

A grant is a UTXO locked by a covenant. It names an agent key, a total budget, a per-spend cap, a per-epoch cap, a validity window, an allowlist of recipients, and a delegation depth.

The word matters. An earlier draft called this a mandate, which is the core noun of AP2 — a protocol this one is meant to sit underneath, not compete with. Reusing it would make every integration conversation begin with a disambiguation. Warda issues grants; AP2 issues mandates; a grant can be the enforcement backend for one.

Grant {
    principalKey       // who may reclaim after expiry
    revocationKey      // who may revoke
    agentKey           // who may spend
    budgetTotal
    maxPerSpend
    epochLimit
    epochLength
    recipientsRoot     // merkle root of the allowlist
    notBefore
    expiresAt
    delegationDepth
    // mutable state — the address is derived from these too
    spentTotal
    reserved
    epochIndex
    epochSpent
}

There is no separate identifier field. A grant's address is the hash of the covenant compiled with its state, so the state is the identity. One consequence is load-bearing and surprises everyone once:

Spending moves the grant. The continuation output goes to a different address, because the address commits to spentTotal and epochSpent.

Sending the remainder back to the input's own address produces an output that no longer matches its own state, and is unspendable forever. Any client that tracks a grant must follow it.

03

Exactly what consensus enforces

This list is the covenant's, not a summary of intent. Each line corresponds to a require in the deployed script.

// every spend
amount > 0
amount <= maxPerSpend
amount <= budgetTotal - (spentTotal + reserved)
amount <= epochLimit - spentThisEpoch
merkleRoot(recipient, proof) == recipientsRoot
claimedDaa >= notBefore
tx.daa >= claimedDaa
successor state follows exactly
checkSig(agentSig, agentKey)
Correction to v0.2

v0.2 listed current_DAA < expires_at as a spend constraint. It is not, and it cannot be. A UTXO covenant only executes when the UTXO is spent, and CLTV expresses "not before", never "must be before". The deployed spend path contains no expiry check.

Expiry is a reclaim right: after expiresAt the principal can sweep the balance, and until they do, the agent's spend path still works. v0.2's lifecycle diagram inherits the same error — nothing on chain performs an EXPIRE transition.

This distinction is not pedantry. A service reading v0.2 would conclude that an expired grant is inert, and it is not. What expiry gives the principal is a unilateral exit, not a guarantee that the agent has stopped.

Why the agent supplies the DAA score

Kaspa's DAA score cannot be read as a value inside a script; it can only be constrained. So the agent asserts a claimedDaa and the covenant pins it with tx.daa >= claimedDaa, which compiles to a lock. Understating it only costs the agent epoch headroom; overstating it is impossible, because the lock would hold the transaction until the chain caught up. The direction that is convenient is also the direction that is sound.

04

Delegation cannot amplify authority

An agent can hand a narrower grant to a sub-agent without asking the principal and without custody. Delegation is a 1:2 fanout: the parent continues at output 0, the child is created at output 1.

// every child
child.budgetTotal      <= parent.budgetTotal - (spentTotal + reserved)
child.maxPerSpend      <= parent.maxPerSpend
child.epochLimit       <= parent.epochLimit
child.epochLength      == parent.epochLength
child.notBefore        >= parent.notBefore
child.expiresAt        <= parent.expiresAt
child.delegationDepth  <  parent.delegationDepth
child.recipientsRoot   == parent.recipientsRoot
child.spentTotal == reserved == epochIndex == epochSpent == 0

// and the parent moves ONLY its reserve
parentNext.reserved == parent.reserved + child.budgetTotal
// every other field checked equal

// value follows authority, exactly
tx.outputs[1].value == child.budgetTotal

Conservation is the property that makes the hierarchy real. The parent reserves precisely what the child receives, and coins move with it. A child holding authority but no coins could pay nobody. A child holding coins but no reserve against its parent would double the tree's total — the same KAS spendable twice, from two addresses, both legitimately.

100 KAS
  │
  ├─ 30 KAS ─► Agent B        A =  50   (100 − 30 − 20)
  │                           B =  30

Recipient narrowing is the one axis that is not yet attenuable. Set inclusion is not decidable from a Merkle root alone, so a child inherits its parent's allowlist verbatim. Narrowing needs per-member inclusion proofs; the reference implementation has a subset witness for it, the covenant does not yet.

05

Settlement modes, and what each one risks

ModeService providedWhat you are trading
Optimistic On valid authority presentation A presentation proves authority existed at the DAA observed. It does not prove the spend will land. An agent can present the same headroom to three services and pay one.
Confirmed After the transaction is accepted Latency. This is the honest default for anything above trivial value.
Escrowed After conditional release Nothing yet — Not built. Escrow is a separate covenant with multi-party release, timeout and dispute paths, not a method on the grant.

Optimistic settlement is right for sub-cent metered calls, where the cost of being double-served is below the cost of waiting. It is worth stating the failure mode explicitly rather than letting an integrator discover it: authority is not a reservation.

06

Verification, and its current limit

A counterparty should be able to answer a sharper question than "does this agent have money":

Is this agent authorized to spend this amount, on this action, right now?

That check is reproducible from public data — the grant's parameters, its current state, and a signed presentation binding the request. No hosted service is required, and no hosted service may be the source of truth. A Warda API can make verification convenient; it must never be able to expand an already-issued grant.

Honest limitation

Confirming a grant exists and is unspent means reading the UTXO set, and the SDK has no node client yet. Today, independent verification means running a node. Until that gap closes, "independently verifiable" is a property of the protocol rather than a convenience of the tooling.

07

Where this sits

Warda replaces none of the protocols agents already speak. It answers a question the others leave open.

LayerAnswers
x402What does this service cost?
MCP / A2AHow do agents call and talk to each other?
AP2What did the user authorize, and how is intent carried?
A walletWhere is the money?
WardaWhat is this agent allowed to spend, on what, until when?
KaspaIs the transaction valid?

The MCP server is the integration that exists today. It exposes four tools — remaining headroom, a spend check, a delegation check, and one that builds an unsigned transaction and returns the digest to sign. It never holds a key. An agent framework can therefore reach a ready-to-sign payment without any Kaspa integration of its own.

Every response it returns carries an enforcement field stating that the answer is advisory. That is not modesty. The server's verdict is not what stops a bad spend; the covenant is. A server whose rules drifted from the chain's would be worse than no server, because it could tell an agent yes where the chain says no.

08

Trust model

The design assumes the agent is compromised. That is the premise, not an edge case.

ComponentTrusted for authority?
The agentNo — assume prompt injection and key compromise
The walletNo — it may sign anything the agent asks
Any hosted Warda serviceNo — optional convenience only
The SDKNo — it lays out bytes; it decides nothing
Kaspa consensusYes — this is the enforcement point

The same principle shapes the SDK's scope. It assembles transactions and refuses to reimplement the rules, because the two failure modes are not symmetric: a divergence in assembly produces a transaction the network rejects, while a divergence in rules produces one it wrongly accepts. Only the second drains a budget.

09

Open questions

  • Recipient narrowing on chain. A subset witness exists in the reference implementation; the covenant enforces root equality only.
  • Descendant revocation. Revoking a parent should invalidate its children. Structural parent-state linkage is the current answer; an accumulator is the alternative.
  • Epoch boundaries. Fixed epochs keep state bounded and make the boundary visible: an allowance resets at a step, not on a rolling window. A sliding window is deferred, deliberately.
  • Escrow topology. Multi-party release and timeout paths in a UTXO covenant are a different design problem from a single-agent grant.
  • Multi-asset. Deferred, because valuing one asset against another needs an oracle and a grant should express 10 KAS, not $10 worth.
  • A node client for the SDK. The gap named in §06, and a prerequisite for a verification product.
10

The question that decides whether this is worth building

The covenant works. That is not the same as the protocol being needed, and the technology being interesting is not evidence either way.

Three statements have to come from someone other than the author:

  • A developer: "I need to give an autonomous agent access to money, and I do not want to give it unrestricted authority."
  • A service provider: "Before I provide this, I want to know the agent is actually authorized to pay for it."
  • Either of them, having integrated it into something real.

Of the commercial directions sketched so far, verification is the only one testable without an enterprise sale — a service provider either wants that call or does not. It is therefore the cheapest experiment, and the one that would answer the second statement directly.
