Money still assumes someone is watching.

An agent can act autonomously at three in the morning, across a thousand API calls, faster than any human reviews. The spending limit protecting you is a row in someone's database, checked by the same service that holds your keys.

So ask the uncomfortable question. What happens when the agent is compromised? When an API key leaks? When a prompt injection rewrites what the agent believes it was asked to do? When a backend is breached — or simply has a bug?

In every one of those cases the limit is enforced by software that has already failed.

Turn authority into an asset.

Instead of recording that an agent is allowed to spend 100 KAS, Warda commits the authority itself to the chain — as a covenant that computes, checks, and refuses.

Assume the agent is compromised.

Warda does not make agents trustworthy. It limits what an untrusted agent can do. A lock's wards don't evaluate a policy — they're a shape, and the wrong key cannot turn.

Attacks that succeed

Each attack is proven by a flip test: a spend the engine accepts, with exactly one field changed. Because the baseline passes, the rejection can only be caused by that field. The engine collapses every failed check into one opaque error — so asserting "it was rejected" against a baseline that never passed would prove nothing at all.

Authority can be delegated. Never amplified.

An agent can hand narrower authority to another agent, and the covenant reserves exactly what it hands over. Total authority in the tree cannot grow.

Principal        100 KAS   max 5
   │
   ├── Agent A     30 KAS   max 2      parent reserves 30
   │      │
   │      └── Agent B   10 KAS  max 1  parent reserves 10
   │
   └── Agent C     20 KAS   max 2      parent reserves 20

Principal's own remaining authority: 50 KAS

Reserving nothing, too little, or too much are all rejected. Over-reserving is safe for the principal and still refused — a covenant that tolerates it has an inequality where it needs an equality, and something sharper will eventually find that.

Warda is not a wallet, a payment processor, or an agent framework. It sits below payment negotiation and above settlement, and it answers exactly one question.

AP2 proves authorization. Warda makes economic authority enforceable at the settlement layer.

A signature attests that someone approved something. A covenant refuses to produce a valid transaction. Those differ in kind, not degree.

What isn't true yet.

Two limits are worth stating plainly, because anyone who understands UTXO systems will find them in minutes.

Expiry is a reclaim right

A covenant cannot forbid a late spend — the timelock primitive expresses "not before", never "not after". After expiry the principal can sweep the balance, and the agent's authority ends when they do.

Revocation doesn't race

Revoking makes the balance unreachable from the next block on. Nothing in a UTXO system retracts a transaction that is already broadcast.

Nothing here has run on mainnet. The protocol is unaudited, the covenant language it targets is pre-1.0, and the hosted services described in the spec do not exist.
