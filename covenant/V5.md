# v5 — what would change, and what has to be proved first

**Nothing here is built, and nothing here touches the deployed covenant.** This
is the design and the probe list for a next covenant version, written down now
so that when a review is funded it covers one version rather than three.

## Why it is a file and not a branch

The review is priced at $20–30k and is not funded. Since the cost is paid per
*version* rather than per change, batching is cheaper than shipping v5 now and
v6 later — that is the argument for writing this down, and it holds.

What does not follow is that changes are free until then. Two costs land
whether or not anybody is paying an auditor:

**A bigger diff is a bigger review.** A quote given against v4 is a quote
against v4's surface. 1:N delegation plus 1:N settlement adds entrypoint
arity, a loop where there is a single check, and a new conservation argument.
Worth confirming with whoever quoted it before treating the number as fixed.

**Every change strands every live grant.** The script is P2SH-committed, so the
address *is* the template. Every grant in this repo — fourteen manifests, the
demo grant behind /attack, the agent fleet, the registry listings, the
coordinator on /one-job — carries `"covenant": "b3e5eeefacf2021f"` and cannot
adopt a new one. A v5 is not an upgrade; it is a second covenant, and the first
one keeps running until each grant is reissued under the new one.

So: design and probes now, deployment deliberately, and v4 stays live
throughout.

---

## Coexistence is already possible — it needs a NAME, not a mechanism

`sdk/src/template.ts` already fingerprints every template:
`templateFingerprint` is blake2b over the full baseline bytecode, truncated to
sixteen hex characters, and `genesis.ts` writes it into every manifest as
`covenant`. A v5 grant gets a different fingerprint on its own, with no change
to the SDK, the console or the site.

**The fingerprint covers the baked parameters as well as the source.** The
template's `baked` block holds `maxProofDepth` and `maxFee`, and those are in
the baseline bytecode. So the same source compiled at depth 16 is a different
fingerprint from the same source at depth 4 — which is correct, because it is a
different script at a different address, but it means a fingerprint is not a
version number. One version has many fingerprints.

What is missing is a map. Proposed: `covenant/versions.json`, keyed by
fingerprint, each entry naming the version, the baked parameters, the date and
what changed — the same shape and the same discipline as
`ops/known-keys.json`, which says how each key is derived rather than merely
asserting what it is. The console and the site then render a label from the
manifest they already hold, and a grant under a fingerprint with no entry shows
its bare fingerprint, which is the honest rendering of a template nobody has
accounted for.

**Worth doing before v5 exists.** Every page today implies there has only ever
been one covenant. Labelling v4 as v4 is a no-op that is already true, and it
means the affordance is built and tested before the first grant that needs it.

## C1 — 1:N delegation

`delegate` is `#[covenant.fanout(to = 2)]` with `OpAuthOutputCount == 2`:
parent continuation at auth output 0, one child at auth output 1. At `to = N+1`
the children are created in one transaction, and from that moment each is its
own UTXO — so this removes "not atomic" and "not concurrent" together.

**Unsettled, and it is the first thing to try.** `#[covenant.fanout]` is
documented as a 1:N construct, but nothing here has compiled it above 2. Until
that is done, everything below is a plan against a feature we have read about.

**Conservation claim.** For children `c₁…c_N`:

    parentNext.reserved == reserved + Σ cᵢ.budgetTotal
    parentNext.spentTotal == spentTotal
    every other parent field unchanged
    each cᵢ attenuated on all six axes against the parent
    each cᵢ.spentTotal == cᵢ.reserved == cᵢ.epochIndex == cᵢ.epochSpent == 0
    the reserve chain carries N pushes, in output order

The equality is the load-bearing part, exactly as at `to = 2`: over-reserving
must be rejected as well as under-reserving, because a covenant that tolerates
a safe error has a comparison a subtler attack will find.

**Probes it needs**, in `covenant/harness/src/bin/audit.rs`, each a single
field away from a baseline that passes:

| case | attempt | expect |
|---|---|---|
| delegation fanout | N properly attenuated children | accept |
| delegation fanout | N+1 children in one delegation | reject |
| delegation fanout | N−1 children where N were reserved | reject |
| conservation | reserve is Σ budgets − 1 | reject |
| conservation | reserve is Σ budgets + 1 | reject |
| conservation | child 2 of 3 reserved twice, child 3 not at all | reject |
| attenuation | child 2 of 3 exceeds the parent on one axis | reject |
| attenuation | the LAST child is the one that exceeds | reject |
| reserve chain | pushes in an order other than output order | reject |
| reserve chain | one child's id omitted from the chain | reject |
| identity | two children with the SAME agent key | reject? — decide |
| subset | child 2 narrows, child 3 widens | reject |

The two worth writing first are the ones a loop gets wrong: **a violation in
the last child rather than the first**, and **the same child counted twice**.
Both pass a check written for one child and applied N times carelessly.

**What it will cost at run time, already measured.** KIP-9 prices the atomic
version, and the price is a floor under each child's budget: 0.17 KAS at 1:2,
0.25 at 1:3, 0.33 at 1:4, 0.65 at 1:8 — about 0.08 more per child, linearly.
An atomic 1:2 of the /one-job workers masses 420,435 against a ceiling of
500,000; 1:3 at 0.2 KAS each masses 770,994 and is refused. `covenant/FANOUT.md`
has the table. **So N is not usefully large, and a template compiled at a big N
would mostly produce transactions the network will not carry.** N = 2 or 3 is
the honest range, which also keeps the stack growth small.

**Stack is the budget to watch.** `LIMITS.md`: size has 115× headroom and
compute 4,096×, but peak stack is 118 of 244. A `delegate` that reads and
checks N children rather than one grows it, and nobody should say it fits until
`used_script_units()` and a per-opcode trace say so at the N that ships.

## C2 — 1:N settlement

Without this, C1 buys nothing on the way out: `reabsorb` consumes parent plus
one child, and settlement pops the reserve chain from the end, so N children
still settle in N transactions.

**Harder than C1, and it should be treated that way.** The existing
`reabsorb` already carries the scar: v4 pre-release accepted settling a child
that still had grandchildren, releasing the parent's full reserve while
charging only the child's spending, and the grandchildren's coin was left
outside every grant's accounting. The fix was `require(child.reserved == 0)`.
Settling N children at once multiplies every surface that bug lived on.

**Conservation claim.**

    newState.reserved   == reserved − Σ cᵢ.budgetTotal
    newState.spentTotal == spentTotal + Σ cᵢ.spentTotal
    newState.spentTotal + newState.reserved <= budgetTotal
    every cᵢ.reserved == 0
    the N ids popped are the LAST N of the chain, in order

**Probes it needs:**

| case | attempt | expect |
|---|---|---|
| settle fanin | the last N children, in chain order | accept |
| settle fanin | the last N, in the wrong order among themselves | reject |
| settle fanin | N children that are not the last N | reject |
| settle fanin | the same child presented at two input indices | reject |
| settle fanin | one of the N still has children of its own | reject |
| settle fanin | a foreign grant of the same template among the N | reject |
| settle fanin | N−1 real children and one decoy that is not a grant | reject |
| accounting | Σ spent charged home is short by one child's | reject |

The decoy cases matter more here than in C1, because `reabsorb` reads foreign
inputs with `readInputStateWithTemplate` and the parent is being asked to
believe N of them rather than one.

## C3 — a deeper allowlist  (NOT a source change)

`maxProofDepth` is a baked constructor parameter, not covenant code. Depth
costs 142 bytes a level, linearly: the shipped templates use 4, which is 16
payees; depth 16 is 65,536 payees at 8,680 bytes — 0.87% of the million-byte
script ceiling, with compute and peak stack unchanged across the whole range
(`LIMITS.md`).

So this is the same audited source at a different parameter, and it gets its
own fingerprint like any other template. It is the cheapest real improvement
available and it needs no version bump — which is an argument for building the
version label first, since a depth-16 template is exactly the case that proves
a fingerprint is not a version number.

It does not make the payee set open. It makes it large.

## What must NOT change

**A child may narrow and never widen.** The asymmetry is the guarantee. Any
proposal that lets a grant add a payee after genesis is a different protocol
wearing this one's name.

**No key may be given authority over the payee set.** Committing to a registry
root that somebody can update moves the guarantee out of the covenant and into
that key — `enforced` becomes `attested` in the router's own vocabulary. That
may be a product worth building, but it must be described as what it is, and a
principal must be able to refuse it.

**The reserve equality stays an equality.** Over-reserving is safe for the
principal and is still rejected, on purpose.

## Order of work

1. `covenant/versions.json` and the label, with v4 as its only entry. No
   covenant change; useful today; the affordance exists before it is needed.
2. Compile `#[covenant.fanout(to = 3)]` and find out whether it is real. Until
   then C1 and C2 are plans against documentation.
3. Write the C1 probes against v4 — the ones that must REJECT already do, since
   v4 refuses two children outright. They are the specification either way.
4. C1, then its probes green, then C2.
5. Measure stack and script units at the N that ships. Do not assume.
6. Only then, a review — of one version, with its probe suite already passing.
