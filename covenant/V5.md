# v5 — what would change, and what has to be proved first

**Nothing here is built, and nothing here touches the deployed covenant.** This
is the design and the probe list for a next covenant version, written down now
so that when a review is funded it covers one version rather than three.

## Why it is a file and not a branch

The review is priced at $20–30k and is not funded. Since the cost is paid per
*version* rather than per change, batching is cheaper than shipping v5 now and
v6 later — that is the argument for writing this down, and it holds.

What does not follow is that changes are free until then. Two costs land
whether or not anybody is paying an auditor:

**A bigger diff is a bigger review.** A quote given against v4 is a quote
against v4's surface. 1:N delegation plus 1:N settlement adds entrypoint
arity, a loop where there is a single check, and a new conservation argument.
Worth confirming with whoever quoted it before treating the number as fixed.

**Every change strands every live grant.** The script is P2SH-committed, so the
address *is* the template. Every grant in this repo — fourteen manifests, the
demo grant behind /attack, the agent fleet, the registry listings, the
coordinator on /one-job — carries `"covenant": "b3e5eeefacf2021f"` and cannot
adopt a new one. A v5 is not an upgrade; it is a second covenant, and the first
one keeps running until each grant is reissued under the new one.

So: design and probes now, deployment deliberately, and v4 stays live
throughout.

---

## Coexistence is already possible — it needs a NAME, not a mechanism

`sdk/src/template.ts` already fingerprints every template:
`templateFingerprint` is blake2b over the full baseline bytecode, truncated to
sixteen hex characters, and `genesis.ts` writes it into every manifest as
`covenant`. A v5 grant gets a different fingerprint on its own, with no change
to the SDK, the console or the site.

**The fingerprint covers the baked parameters as well as the source.** The
template's `baked` block holds `maxProofDepth` and `maxFee`, and those are in
the baseline bytecode. So the same source compiled at depth 16 is a different
fingerprint from the same source at depth 4 — which is correct, because it is a
different script at a different address, but it means a fingerprint is not a
version number. One version has many fingerprints.

What is missing is a map. Proposed: `covenant/versions.json`, keyed by
fingerprint, each entry naming the version, the baked parameters, the date and
what changed — the same shape and the same discipline as
`ops/known-keys.json`, which says how each key is derived rather than merely
asserting what it is. The console and the site then render a label from the
manifest they already hold, and a grant under a fingerprint with no entry shows
its bare fingerprint, which is the honest rendering of a template nobody has
accounted for.

**Worth doing before v5 exists.** Every page today implies there has only ever
been one covenant. Labelling v4 as v4 is a no-op that is already true, and it
means the affordance is built and tested before the first grant that needs it.

## C1 — 1:N delegation

`delegate` is `#[covenant.fanout(to = 2)]` with `OpAuthOutputCount == 2`:
parent continuation at auth output 0, one child at auth output 1. At `to = N+1`
the children are created in one transaction, and from that moment each is its
own UTXO — so this removes "not atomic" and "not concurrent" together.

**Unsettled, and it is the first thing to try.** `#[covenant.fanout]` is
documented as a 1:N construct, but nothing here has compiled it above 2. Until
that is done, everything below is a plan against a feature we have read about.
`covenant/probes/run-fanout.sh` asks the question and nothing else: a minimal
contract with no attenuation, no conservation and no reserve chain, because
those are C1's real work and every one of them would raise compiler errors
that mask the one being asked about.

**Result, 24 September 2026: it compiles.** `to = 2, 3, 4, 5` all compile, and
the script grows linearly — 367, 460, 553, 646 bytes, **+93 bytes per child**
for one `require` each. At N = 3 the probe is 0.046% of the million-byte
ceiling. Script size is not the constraint and was never going to be.

What that does NOT establish is that the chain will authorise N outputs from
one input. The compiler emits a script; whether rusty-kaspa's covenant
machinery accepts it is a separate question, and `scan` says so about itself —
compute and peak stack are measured from an execution, not from source. That is
what `cargo run --release --bin fanout` asks, through `TxScriptEngine`, the
engine the network runs.

**Engine result, 24 September 2026: accepted, at every N tried.**

| to | bytes | script units | engine |
|---:|---:|---:|---|
| 2 (control) | 367 | 4,490 | accepted |
| 3 | 460 | 7,591 | accepted |
| 4 | 553 | 11,468 | accepted |
| 5 | 646 | 16,121 | accepted |
| 8 | 925 | 34,768 | accepted |

**Units grow quadratically, and that is the finding.** The second differences
are a constant 776, so the cost is exactly `388N² + 1161N + 616` — it fits
N = 2..5 to the unit and N = 8 to within 32. Bytes are linear and units are
not, which means the array access is: reaching `newStates[i]` costs something
proportional to `i`, so N of them costs N².

It does not bind. One signature verification is 100,000 script units on its
own, so the whole transaction is 104,490 units at N = 2 and 134,768 at N = 8 —
**11 and 14 budget units against a u16 ceiling of 65,535.** The quadratic is
real and the signature damps it: going from 2 children to 8 multiplies the
covenant's own work by 7.7 and the transaction's total by 1.29. Compute is
charged as mass, so that 1.29 is a fee difference rather than a free margin,
but it is not a wall.

**So three of the four constraints say yes.** The attribute compiles, the
script stays at a fraction of a percent of the size ceiling, and the engine
authorises N outputs from one input. Storage mass is the only one that refuses,
and it refuses at N = 3 — see `covenant/FANOUT.md`. That convergence is worth
stating plainly: **atomic delegation is bounded by KIP-9 and by nothing else we
have measured.**

**Still unmeasured: peak stack.** `measure_units` does not report it; the
118-of-244 figure in `LIMITS.md` came from reading a per-opcode trace. And the
probe's body is trivial, so its stack says nothing about a real `delegate` at
N. That measurement belongs to C1, against C1's actual body, and step 5 stands.

**Conservation claim.** For children `c₁…c_N`:

    parentNext.reserved == reserved + Σ cᵢ.budgetTotal
    parentNext.spentTotal == spentTotal
    every other parent field unchanged
    each cᵢ attenuated on all six axes against the parent
    each cᵢ.spentTotal == cᵢ.reserved == cᵢ.epochIndex == cᵢ.epochSpent == 0
    the reserve chain carries N pushes, in output order

The equality is the load-bearing part, exactly as at `to = 2`: over-reserving
must be rejected as well as under-reserving, because a covenant that tolerates
a safe error has a comparison a subtler attack will find.

**Built, and its flips pass — 24 September 2026.** `covenant/warda_grant_v5.sil`
is v4 plus `delegate2` and nothing else. `cargo run --release --bin c1` gets two
accepted baselines and refuses all eight flips:

```
two children, honest              ACCEPTED   (baseline)
60 KAS already reserved, 5 + 5    ACCEPTED   (baseline for the sequential bound)
each fits, together they do not   refused
both children under one key       refused
chain pushed B then A             refused
reserve is the sum minus one      refused
reserve is the sum plus one       refused
the LAST child exceeds maxPerSpend    refused
the FIRST child exceeds maxPerSpend   refused
the LAST child starts with spentTotal 1   refused
```

`delegate` is untouched and still creates one child, which is required rather
than cautious: `fanout(to = N)` fixes the authorised output count exactly, so a
covenant carrying only `delegate2` could not hire a single worker.

Costs, from `scan`: 10,198 bytes against v4's 6,912 at the same arguments —
1.02% of the ceiling — and 56 conditions in `delegate2` against 38 in
`delegate`. **It doubles the price of C3**: `maxProofDepth` 4 → 8 now costs
+1,136 bytes where v4 charged +568, because `delegate2` adds two more
`foldFromNode` calls and each unrolls at the baked depth. 284 bytes a level
instead of 142, so depth 16 would be ~13,600 bytes. Still nothing, and the two
changes are now coupled where they were not.

**Settling what it creates — tested, and it works.** v4's `reabsorb` settles
`delegate2`'s children unchanged:

```
CONTROL: one child, one chain   ACCEPTED   (the settle builder itself)
settle B (hired last)           ACCEPTED
then settle A                   ACCEPTED   reserved back to 0, chain empty again
settle A first, out of order    refused
```

So **C2 is an optimisation, not a prerequisite**, and that is now evidence
rather than reasoning. The chain `delegate2` builds is
`H(H(empty || cidA) || cidB)`; popping from the end gives B then A, which is
what `reabsorb` already checks, and the LIFO discipline refuses A first with no
new rule. `delegate2` is shippable on its own.

*What the control cost, and why it was worth it.* The first run of the
settlement probe refused everything and printed that C2 was a prerequisite and
this file was wrong. It had no standing to say so: the settle builder was new
and had never been proved against anything, so its refusal was a sentence about
the builder. Adding a control — settle a single-child chain, a shape v4's own
tests settle — turned one confident wrong answer into two real bugs, both of
the same shape: **a field nothing in the happy path reads stays wrong until
something reads it.** The grants were built under `default_authority`'s
placeholder keys, which `delegate` and `delegate2` never check and `settle`
does; and the child builder dropped the child's accounting, which is all zeroes
for a newborn and not for one that has spent.

**Probes it needs**, in `covenant/harness/src/bin/audit.rs`, each a single
field away from a baseline that passes:

| case | attempt | expect |
|---|---|---|
| delegation fanout | N properly attenuated children | accept |
| delegation fanout | N+1 children in one delegation | reject |
| delegation fanout | N−1 children where N were reserved | reject |
| conservation | reserve is Σ budgets − 1 | reject |
| conservation | reserve is Σ budgets + 1 | reject |
| conservation | child 2 of 3 reserved twice, child 3 not at all | reject |
| attenuation | child 2 of 3 exceeds the parent on one axis | reject |
| attenuation | the LAST child is the one that exceeds | reject |
| reserve chain | pushes in an order other than output order | reject |
| reserve chain | one child's id omitted from the chain | reject |
| identity | two children with the SAME agent key | reject? — decide |
| subset | child 2 narrows, child 3 widens | reject |

The two worth writing first are the ones a loop gets wrong: **a violation in
the last child rather than the first**, and **the same child counted twice**.
Both pass a check written for one child and applied N times carelessly.

**What it will cost at run time, already measured.** KIP-9 prices the atomic
version, and the price is a floor under each child's budget: 0.17 KAS at 1:2,
0.25 at 1:3, 0.33 at 1:4, 0.65 at 1:8 — about 0.08 more per child, linearly.
An atomic 1:2 of the /one-job workers masses 420,435 against a ceiling of
500,000; 1:3 at 0.2 KAS each masses 770,994 and is refused. `covenant/FANOUT.md`
has the table. **So N is not usefully large, and a template compiled at a big N
would mostly produce transactions the network will not carry.** N = 2 or 3 is
the honest range, which also keeps the stack growth small.

**Stack is the budget to watch.** `LIMITS.md`: size has 115× headroom and
compute 4,096×, but peak stack is 118 of 244. A `delegate` that reads and
checks N children rather than one grows it, and nobody should say it fits until
`used_script_units()` and a per-opcode trace say so at the N that ships.

## C2 — 1:N settlement  (optional, and now demonstrably so)

**Not a prerequisite.** `delegate2`'s children settle one at a time through
v4's `reabsorb`, unchanged and proven above. What C2 would buy is symmetry: two
children hired in one transaction still come home in two, so an atomic
delegation is not an atomic settlement.

That is a smaller prize than it looked, and it should be weighed against the
cost below before anyone writes it.

**Harder than C1, and it should be treated that way.** The existing
`reabsorb` already carries the scar: v4 pre-release accepted settling a child
that still had grandchildren, releasing the parent's full reserve while
charging only the child's spending, and the grandchildren's coin was left
outside every grant's accounting. The fix was `require(child.reserved == 0)`.
Settling N children at once multiplies every surface that bug lived on.

**Conservation claim.**

    newState.reserved   == reserved − Σ cᵢ.budgetTotal
    newState.spentTotal == spentTotal + Σ cᵢ.spentTotal
    newState.spentTotal + newState.reserved <= budgetTotal
    every cᵢ.reserved == 0
    the N ids popped are the LAST N of the chain, in order

**Probes it needs:**

| case | attempt | expect |
|---|---|---|
| settle fanin | the last N children, in chain order | accept |
| settle fanin | the last N, in the wrong order among themselves | reject |
| settle fanin | N children that are not the last N | reject |
| settle fanin | the same child presented at two input indices | reject |
| settle fanin | one of the N still has children of its own | reject |
| settle fanin | a foreign grant of the same template among the N | reject |
| settle fanin | N−1 real children and one decoy that is not a grant | reject |
| accounting | Σ spent charged home is short by one child's | reject |

The decoy cases matter more here than in C1, because `reabsorb` reads foreign
inputs with `readInputStateWithTemplate` and the parent is being asked to
believe N of them rather than one.

## C3 — a deeper allowlist  (NOT a source change)

`maxProofDepth` is a baked constructor parameter, not covenant code. Depth
costs 142 bytes a level, linearly: the shipped templates use 4, which is 16
payees; depth 16 is 65,536 payees at 8,680 bytes — 0.87% of the million-byte
script ceiling, with compute and peak stack unchanged across the whole range
(`LIMITS.md`).

So this is the same audited source at a different parameter, and it gets its
own fingerprint like any other template. It is the cheapest real improvement
available and it needs no version bump — which is an argument for building the
version label first, since a depth-16 template is exactly the case that proves
a fingerprint is not a version number.

It does not make the payee set open. It makes it large.

---

## What must NOT change

**A child may narrow and never widen.** The asymmetry is the guarantee. Any
proposal that lets a grant add a payee after genesis is a different protocol
wearing this one's name.

**No key may be given authority over the payee set.** Committing to a registry
root that somebody can update moves the guarantee out of the covenant and into
that key — `enforced` becomes `attested` in the router's own vocabulary. That
may be a product worth building, but it must be described as what it is, and a
principal must be able to refuse it.

**The reserve equality stays an equality.** Over-reserving is safe for the
principal and is still rejected, on purpose.

## Order of work

0. **v5's template is built. Its fingerprint is `157b64e3eeea9c01`**, recorded
   in `covenant/versions.json` and in GUARANTEES.md's table, and
   `ops/check-versions.mjs` re-derives it from `sdk/covenant-template-v5.json`
   like every other entry. 10,375 bytes, state region 1..232, and — the part
   that matters for the SDK — **splice == compile, byte-identical across
   authority and state**, so JavaScript can derive a v5 address without a
   compiler, exactly as it does for v4.

   `warda-deploy template --v5` builds it, and writes
   `covenant-template-v5.json` rather than `covenant-template.json`. The first
   attempt at that guard compared `std::ptr::eq(src(), SOURCE_V5)`, which is
   always false for a `const &str` — the build was correct and its output
   overwrote v4's template. Restored from git, which is the only reason it cost
   nothing.

   **And it is on chain.** `b488d1e3492e2a03c37c622747225ed246fdd8ecf5081443879bcb5e50bbde50`
   put 0.8 KAS at
   `kaspatest:prhjj9thzdxtzcmc8dfr5t5uhw4sfc4yczjhl0x6kleknhacqmavct2zq5dmx`
   under covenant `157b64e3eeea9c01` — the first grant here that is not v4 —
   and `verify-grant.ts --template covenant/deploy/covenant-template-v5.json`
   says *the chain agrees with this manifest*: the address JavaScript derived
   by splicing the template is the address holding the coin, and the covenant
   id matches. That is the template checked against consensus rather than
   against the harness, and the two could have disagreed.

   Its allowlist is /one-job's two sellers and its budget is what the mass
   table says an atomic 1:2 needs, so it is the grant the first `delegate2`
   call will be made from. Today it can spend, delegate ONE child, revoke and
   reclaim — every v4 path, since `delegate` is untouched.

   *Worth recording:* `verify-grant` refused the first attempt, because the
   manifest names covenant `157b64e3eeea9c01` and the packaged template is
   `b3e5eeefacf2021f`. That refusal has been in the code since manifests
   started carrying a fingerprint and had never been able to fire — with one
   covenant in existence there was nothing for it to catch.

1. `covenant/versions.json` and the label, with v4 as its only entry. No
   covenant change; useful today; the affordance exists before it is needed.
2. Compile `#[covenant.fanout(to = 3)]` and find out whether it is real:
   `covenant/probes/run-fanout.sh`, which materialises one template at several
   values of N so the only difference between the artefacts is the number, and
   treats `to = 2` as a control that must pass. Until it has run, C1 and C2 are
   plans against documentation, and this file should say so.
3. Write the C1 probes against v4. **Done, 24 September 2026:**
   `cargo run --release --bin c1`. Twelve cases, each carrying the rule that
   must do the refusing. The N-child builder is proved — at N = 1 it produces a
   transaction the engine accepts, and an under-reserve and an over-reserve
   flipped from that baseline are both refused, reproducing audit.rs's
   conservation result through the new builder. Four cases have an N = 1 form
   v4 covers; **seven are pending and print as pending**, because on v4 they
   are refused by the arity before any rule they name is reached, and the
   engine's message is the same sentence for every refusal. A probe that fails
   for the wrong reason is worse than no probe.
4. C1, then its probes green, then C2. **C1 is done and the SDK can build it.**
   `buildUnsignedDelegation2` in `sdk/src/delegate.ts` produces a signature
   script byte-for-byte identical to the transaction `TxScriptEngine` accepted,
   the same sighash, and all three outputs — checked against
   `sdk/golden-delegation2.json`, which is emitted from that accepted
   transaction rather than from a builder.

   Two findings came out of that comparison, and neither was reachable any
   other way:

   - **maxFee is baked, not spliced.** The SDK reproduced 1,879 bytes of an
     11,120-byte script and then diverged: 100,000 against 5,000,000. A golden
     emitted at the harness's maxFee can never be reproduced from the deployed
     template, however correct the builder.
   - **templateId depends on maxFee.** Fixing the first broke every
     settlement. The id is a blake3 over the compiled prefix and suffix and
     maxFee sits in the suffix — but both values encode in three script bytes,
     so the geometry never moved and every address still derived. `delegate2`
     only requires the child's id to EQUAL the parent's, and both were the same
     wrong value. `reabsorb` and `settle` are the only paths that USE it, and
     they are the only ones that refused. **A grant issued at one maxFee and
     settled against an id computed at another can delegate and can never come
     home.**

   The SDK now asserts the vector's templateId is what `templateIdFor` derives
   from the template — the only test in that file a wrong id could not pass.
5. Measure stack and script units at the N that ships. Do not assume.
6. Only then, a review — of one version, with its probe suite already passing.
